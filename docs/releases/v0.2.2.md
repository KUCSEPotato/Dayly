## Added

### 사용자 지정 태그

- `GET /api/tags`로 태그를 조회하고 `POST /api/tags`로 이름·색상을 지정하여 생성합니다. `q` 검색은 정규화된 이름의 부분 문자열을 기준으로 하며 `%`, `_`는 검색 와일드카드로 취급하지 않습니다.
- Task 생성·수정 폼에서 기존 태그 검색·선택, 즉시 새 태그 생성, 개별 지정 해제를 지원합니다. 지정 해제는 Task나 태그 자체를 삭제하지 않습니다.
- 하나의 Task에 여러 태그를 연결하고 여러 Task가 같은 태그를 재사용합니다. 사용하지 않는 태그도 보존합니다.
- 이름은 앞뒤 공백 제거 후 1~30자입니다. 별도 `normalized_name`에 Unicode `casefold()` 결과를 저장하여 대소문자만 다른 이름의 중복 생성을 방지합니다.
- 같은 이름으로 생성 요청이 반복되면 기존 태그를 반환합니다. 최초 이름·색상을 유지하고 HTTP 201을 반환합니다. 동시 요청도 기존 직렬화 트랜잭션과 DB 고유 제약으로 보호합니다.
- 색상은 초록 `#7c956b`(기본), 파랑 `#648ca6`, 보라 `#a183b5`, 주황 `#c48b65`, 분홍 `#bd7887`, 노랑 `#aa994f` 중 선택합니다. 다른 색상은 422로 거부합니다.
- 목록에는 Task 제목 앞에 작은 색상 상자와 태그 이름을 표시합니다. 긴 이름·여러 태그는 줄바꿈하며 완료 상태에서도 태그를 유지합니다. 새 회고의 Task 목록에도 당시 태그를 표시합니다.

### 다음 날로 미루기

- Task 목록의 수정·삭제 버튼 사이에 달력/화살표 버튼을 추가했습니다. Tooltip과 접근성 이름은 `다음 날로 미루기`입니다.
- 서버가 현재 저장된 `scheduled_date`에 하루를 더합니다. 오늘 기준으로 옮기거나 Task를 삭제·재생성하지 않습니다. 미래 날짜·월말·연말·윤년을 처리합니다.
- ID, 제목, 설명, 태그, 생성 시각을 유지하고 수정 시각만 기존 UTC 정책에 맞춰 갱신합니다.
- 완료된 Task는 버튼을 비활성화하고 서버에서도 403으로 거부합니다. 기존 최근 7일/미래 날짜 접근 정책을 그대로 적용합니다. `9999-12-31`에서의 날짜 초과도 403으로 처리합니다.
- 성공 후 선택 날짜를 유지하면서 Task 목록·달력·오늘/최근 7일 달성률을 다시 불러옵니다. 다음 날짜로 자동 이동하거나 페이지를 새로고침하지 않습니다.
- 성공 안내를 표시하고, 요청 실패 시 기존 화면의 Task 상태를 유지합니다. 요청 처리 중 버튼 비활성화와 요청 잠금으로 중복 클릭을 막습니다.

## Changed

### 계층별 책임

- **Router**: 태그 조회/생성, 미루기 요청의 입력·응답 계약을 제공합니다. 실제 정책과 저장은 Service에 위임합니다.
- **Pydantic Schema**: 태그 이름·팔레트·양의 정수 ID를 검증하고 Task 응답에 `tags`를 추가합니다. 기존 Task 필드 계약은 유지합니다.
- **SQLAlchemy Model**: `Tag`와 `task_tags` 연결 테이블로 다대다 관계를 표현하고 중복 연결을 복합 기본 키로 차단합니다.
- **Service Layer**: 태그 재사용/정규화, 태그 존재 여부, 실질적 변경 판별, 미루기 제약 및 변경·이벤트의 원자적 저장을 담당합니다.

### Task Events / 회고 / XP 호환성

- 태그 추가·제거는 기존 `UPDATED` 이벤트를 사용합니다. 완료 변경과 함께 요청하면 기존 `COMPLETED`/`UNCOMPLETED` 이벤트 하나에 모든 상태를 담습니다.
- 이벤트의 `before_state`, `after_state`에는 당시 태그의 `id`, `name`, `color`를 저장합니다. 과거 복원은 현재 `tags` 테이블을 조회하지 않습니다.
- 태그 ID의 중복 또는 순서 변경만 있는 요청은 같은 구성으로 간주합니다. 연결은 태그 ID 순으로 반환하고 불필요한 이벤트·수정 시각 변경을 만들지 않습니다.
- 미루기는 기존 `UPDATED` 이벤트에 `change_reason="POSTPONED"`를 기록합니다. 일반 날짜 수정과 구분하되 새로운 이벤트 종류는 추가하지 않았습니다.
- Task·연결·이벤트를 같은 직렬화 트랜잭션에 저장합니다. 존재하지 않는 태그 또는 이벤트 저장 실패 시 전체 변경을 롤백합니다.
- 예전 이벤트 JSON은 수정하지 않았습니다. `tags`가 없는 과거 상태는 복원 시 빈 태그로 해석합니다.
- 기존 회고 JSON은 다시 계산하거나 현재 태그로 보충하지 않습니다. 회고 API는 미설정 기본 필드를 생략하여 태그가 없던 기존 회고 응답도 유지합니다. 신규 회고는 날짜 종료 시점의 이벤트에서 당시 태그와 예정 날짜를 복원합니다.
- 태그 변경과 미루기 자체에는 XP를 지급하지 않습니다. 최초 완료 XP는 같은 Task ID당 한 번만 지급하며 기존 지급 내역·확정 보너스·레벨 공식을 변경하지 않습니다. XP 정책 버전도 `v0.2.1-provisional`을 유지합니다.
- 앱 및 패키지 버전은 `0.2.2`로 갱신했습니다. 런타임 의존성은 추가하지 않았습니다.

## Database / Migration

새 Alembic revision은 **`0004`**, 이전 revision은 `0003`입니다.

| 변경 | 역할 |
| --- | --- |
| `tags` | `id`, `name`, 고유한 `normalized_name`, `color`, UTC `created_at`/`updated_at` 저장 |
| `task_tags` | `(task_id, tag_id)` 복합 기본 키와 외래 키로 Task–Tag 연결 관리 |
| `task_events.change_reason` | 변경 사유를 담는 nullable `VARCHAR(32)` 필드 |

기존 `tasks` 테이블과 Task ID는 유지합니다. Task 삭제 시 연결만 제거하고 태그 및 Task Events를 보존합니다. 기존 Task는 태그 없는 상태로 시작하며 과거 기록에 태그를 임의로 생성하지 않습니다. 이벤트·회고·XP의 append-only/immutable 보호도 유지합니다.

개발 볼륨을 읽기 전용으로 연결하여 SQLite backup API로 `backend/data/backups/v0.2.2-before-20261125.db`에 백업했습니다. 백업은 Git 및 Docker 빌드에서 제외됩니다. 백업 복사본을 `0003 → 0004`로 올린 후 원본 열의 모든 행, 이력 추적 시작 시각, `PRAGMA integrity_check`, `alembic check`, 반복 upgrade를 검증했습니다.

검증 당시 실제 개발 DB는 Task·이벤트·회고·XP 행이 0개였으므로, 별도로 모든 기록이 들어 있는 v0.2.1 테스트 DB를 구성해 마이그레이션 전후 값과 회고 API 응답을 비교했습니다. 운영 DB는 마이그레이션하거나 테스트에 사용하지 않았습니다.

개발 Docker 시작 시 기존 스크립트가 자동으로 `alembic upgrade head`를 실행합니다. 직접 실행하는 별도 개발 DB에서는 Backend 디렉터리에서 다음 명령을 사용합니다.

```sh
uv run alembic upgrade head
uv run alembic check
```

## API Changes

| Method | Endpoint | 설명 |
| --- | --- | --- |
| GET | `/api/tags?q=Python` | 전체 태그 또는 이름 부분 검색 결과 조회 |
| POST | `/api/tags` | 이름·팔레트 색상으로 생성, 정규화된 이름이 같으면 기존 태그 재사용 |
| POST | `/api/tasks/{id}/postpone` | 서버에 저장된 예정 날짜의 다음 날로 이동, 응답 200 |
| POST | `/api/tasks` | 기존 생성 필드에 선택적 `tag_ids` 추가 |
| PATCH | `/api/tasks/{id}` | 기존 수정 필드에 선택적 `tag_ids` 추가 |
| GET | `/api/tasks?date=YYYY-MM-DD` | 기존 응답에 `tags: [{id, name, color}]` 추가 |

태그 생성 예시:

```json
{ "name": "Python", "color": "#648ca6" }
```

Task 생성 예시:

```json
{
  "title": "FastAPI 테스트 코드 작성",
  "scheduled_date": "2026-11-25",
  "tag_ids": [1, 3]
}
```

수정 시 `tag_ids`를 생략하면 기존 태그를 유지하고, `[]`이면 모두 해제합니다. `null`, 0/음수/문자열 ID는 422이며 존재하지 않는 ID는 404입니다. 같은 ID의 중복 지정은 한 번의 연결로 처리합니다. 미루기는 요청 본문이 필요하지 않습니다.

개발 OpenAPI: `http://localhost:8081/docs` (스키마: `http://localhost:8081/openapi.json`).

개발 서버의 Backend/Frontend는 `healthy`, DB는 `0004 (head)`입니다. 실제 개발 DB의 기존 열 전체 해시를 백업과 비교하여 동일함을 확인했고 홈페이지·문서·OpenAPI·태그·Task 조회는 HTTP 200을 반환했습니다. 운영 컨테이너 ID와 시작 시각은 작업 전후 동일합니다. QA 컨테이너·볼륨은 최종 검증 후 제거했습니다.

## Known Limitations

- 태그 이름 변경·전체 삭제·별도 관리 페이지, 태그별 통계/회고/XP는 이번 범위에서 제외합니다. 사용하지 않는 태그는 계속 목록에 남습니다.
- 태그 표시는 ID 순으로 고정하며 별도의 사용자 지정 정렬 순서는 저장하지 않습니다. 조회 API에는 페이지네이션이 없습니다.
- 미루기는 한 Task를 예정 날짜의 다음 날로 이동하는 기능입니다. 임의 기간·일괄 미루기·반복 일정·미루기 패턴 분석은 제공하지 않습니다.
- Frontend는 처리 중 재요청을 막지만 API 자체는 멱등적이지 않습니다. 여러 클라이언트가 각각 성공한 미루기 요청을 보내면 성공 요청마다 하루 이동합니다.
- 새 태그를 만든 뒤 Task 저장을 취소하거나 실패해도 태그는 재사용할 수 있도록 보존합니다.
- Forest/Ocean 성장 화면과 기존 XP/레벨 공식 변경은 포함하지 않습니다. 기존 전체 이력 재생에 따른 집계 비용도 이번 버전에서 변경하지 않았습니다.
