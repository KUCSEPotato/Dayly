# v0.2.3 · 태그별 회고 분석과 날짜 지정 미루기

기존 일간·주간·월간 회고에 태그별 활동과 미루기 분석을 추가했습니다. 미루기는 기존의 다음 날 이동과 함께 원하는 이후 날짜로 한 번에 이동하는 기능을 제공합니다. 전체 달성률·고정 회고·XP 정책은 유지합니다.

## Added

### 태그별 활동 분석

- 날짜별 종료 시점에 복원한 Task 사본으로 태그별 전체·완료·미완료 개수와 달성률을 집계합니다.
- 주간·월간 달성률은 `완료 합계 / 전체 합계 × 100`입니다. 일별 비율의 단순 평균은 사용하지 않습니다.
- 다중 태그 Task는 각 태그에 포함하고, 태그가 없는 항목은 `태그 없음`으로 분류합니다. 전체 회고 개수는 기존 계산을 유지합니다.
- 기존 정책대로 서로 다른 예정 날짜의 종료 기록에 같은 Task가 나타나면 날짜별 계획으로 각각 집계합니다. 태그 활동 개수는 기간 전체의 고유 Task 수를 뜻하지 않습니다.
- 태그는 이름이 아닌 ID로 구분하고 당시 이벤트에 저장된 이름·색상을 사용합니다. 현재 Task/Tag 테이블의 값을 과거 기록에 덮어쓰지 않습니다.
- 완료 수가 많은 순으로 정렬하며, 동률이면 전체 개수·태그 ID 순으로 정렬합니다. 이름·색상은 해당 분석 입력에서 마지막으로 관측한 값을 표시합니다.
- 완료/계획이 가장 많은 실제 태그를 사실에 기반한 문구로 표시합니다. 같은 최댓값은 모두 공동으로 표시하며, 완료 수가 0이면 완료 관련 문구를 생략합니다. 중요도·소요 시간·성과를 추정하지 않습니다.

### 미루기 분석

| 지표 | 계산 |
| --- | --- |
| 미룬 할 일 | 기간 내 성공한 미루기 이벤트의 고유 Task ID 개수 |
| 전체 미루기 횟수 | 기간 내 `UPDATED` + `change_reason="POSTPONED"` 이벤트 개수 |
| 누적 연기 일수 | 각 미루기의 `after_state.scheduled_date - before_state.scheduled_date` 합계 |

하나의 Task를 3일 미룬 뒤 2일 미루면 **할 일 1개 · 2회 · 5일**입니다. 누적 연기 일수는 미루기 행동의 날짜 이동량 합계이며 최초 예정일 대비 최종 지연 기간과는 다릅니다. 수정 기능에서 날짜를 앞으로/뒤로 바꾼 것은 포함하지 않습니다.

- 미루기를 실행한 시각이 회고의 서울 시간 `[시작, 종료)` 범위 안에 있는지로 판단합니다. 이전·변경 후 예정 날짜는 기간 포함 여부에 사용하지 않습니다.
- 이벤트의 `before_state`에 저장된 태그로 분류합니다. 미루기는 태그를 바꾸지 않으므로 해당 이벤트의 전후 태그는 같습니다.
- 다중 태그는 각 태그의 세 지표에 포함하되 전체 통계에서는 Task와 이벤트를 중복 집계하지 않습니다. 태그별 합계와 전체 값이 다를 수 있습니다.
- 이후 태그를 바꾸거나 Task를 삭제해도 이전 이벤트의 분석은 유지됩니다. 실패한 요청은 이벤트를 만들지 않으므로 집계되지 않습니다.
- **v0.2.2의 하루 단위 미루기도 각각 1회·1일로 계산합니다.** 이전 UI에서 여러 날을 미루려면 버튼을 반복해서 눌러야 했으므로 과거 미루기 횟수가 많게 기록되었을 수 있습니다. 시간 간격에 따른 임의 그룹화·이벤트 병합은 수행하지 않습니다.

### 날짜 지정 미루기

- 미루기 버튼을 누르면 `다음 날로 미루기`, `날짜 직접 지정` 팝오버를 표시합니다.
- 다음 날 이동은 오늘이 아닌 기존 예정 날짜를 기준으로 합니다. 직접 지정은 해당 날짜보다 이후 날짜만 허용하고 `미루기 확인`을 눌러야 반영됩니다.
- 여러 날 이동도 API 요청·Task 변경·이벤트를 각각 한 번만 처리합니다. Task ID·제목·설명·태그·생성 시각 등은 유지하고 예정 날짜·수정 시각만 갱신합니다.
- 같은 날짜·이전 날짜·완료된 Task는 서버에서도 거부합니다. 기존 최근 7일/미래 날짜 접근 정책과 날짜 상한을 유지합니다. 이전 날짜 이동은 기존 수정 폼을 사용합니다.
- 성공 시 목록·달력·달성률을 새로 조회하며 선택된 날짜와 화면은 유지합니다. 요청 중 중복 클릭을 차단하고 실패 시 선택한 날짜·기존 Task를 유지합니다.
- 바깥 클릭·Escape로 닫을 수 있고 키보드 포커스를 지원합니다. 화면 크기가 바뀌어도 팝오버를 뷰포트 안에 배치합니다.

## Changed

### 회고 UI와 Snapshot

- 기존 회고 화면에 공통 `태그별 활동`, `미루기 현황` 패널을 추가했습니다. 태그 배지·Progress Bar·기존 색상과 카드 스타일을 재사용합니다.
- 여섯 개를 넘는 태그는 더 보기/접기로 표시합니다. 실제 미루기 기록이 0이면 별도 태그 목록을 표시하지 않습니다.
- 신규 Snapshot의 기존 JSON `data`에 `analysis`를 저장합니다. 회고 생성 시 확정하며 이후 조회에는 저장된 분석을 반환합니다.
- v0.2.1/v0.2.2 Snapshot에는 분석 필드를 추가하거나 재계산하지 않습니다. 기존 응답에서 빠진 필드는 계속 생략하고 UI에는 상세 분석 도입 전 기록이라는 안내를 표시합니다.
- 분석에는 이미 복원한 날짜별 상태와 `TaskHistoryService.events_between()`을 재사용합니다. 같은 집계에서 날짜 상태를 다시 복원하지 않고, 한 번의 이벤트 범위 조회로 기록 범위 확인과 미루기 집계를 처리합니다.
- Tag 생성·지정·해제·미루기는 추가 XP를 만들지 않습니다. 기존 최초 완료 중복 방지·확정 보너스·레벨 공식·`v0.2.1-provisional` 정책은 변경하지 않았습니다.

### 분석 가능한 기록의 범위

v0.2.2 도입 시각은 별도 저장되어 있지 않습니다. 불확실한 과거를 0으로 표시하지 않기 위해, 이력 추적 시작 이후 **이벤트 상태 JSON에 `tags` 필드가 명시된 최초 기록**을 태그·미루기 분석 가능 범위의 보수적인 시작 증거로 사용합니다. v0.2.2는 태그가 없어도 `tags: []`를 새 이벤트에 기록하며 명시적인 미루기 사유도 함께 도입했습니다.

| `analysis.coverage.status` | 의미와 표시 |
| --- | --- |
| `complete` | 기간 시작 시점부터 기록을 확인할 수 있음. 태그 활동과 미루기 수치 제공, 실제 기록 없음은 0 |
| `partial` | 기간 도중 기록을 확인하기 시작함. 시작 시각을 알리고 전체 기간 수치는 제공하지 않음 |
| `unavailable` | 기간 종료 전까지 도입 이후 기록의 증거가 없음. 실제 0과 구분하며 수치는 null |

부분/분석 불가 기간은 태그 목록을 비우고 미루기 세 지표를 `null`로 저장합니다. 화면에서도 0회처럼 표시하지 않습니다. 기존 전체 회고의 부분 기록 계산 방식은 그대로 유지합니다.

이 방식은 설치·업데이트 시각을 추측하거나 새로운 DB 추적 필드를 추가하지 않습니다. 실제로 v0.2.2를 실행했어도 첫 Task 변경 이벤트가 생기기 전 기간은 분석 불가일 수 있습니다. 최초 기록이 있는 날짜도 중간 시각부터 시작했다면 그 날 전체 분석은 제공하지 않습니다. 이미 생성된 Snapshot에 이후 증거를 소급 적용하지 않습니다.

## Database / API Changes

### 데이터베이스

**새 마이그레이션은 없습니다. 최신 revision은 `0004`입니다.** 기존 JSON Snapshot과 이벤트의 `before_state`, `after_state`, `occurred_at`, `change_reason`만 사용합니다. 별도의 연기 일수 컬럼이나 이벤트 그룹 테이블은 추가하지 않았습니다.

개발 DB는 작업 전 `backend/data/backups/v0.2.3-before-20261126.db`에 SQLite backup API로 백업했습니다. 백업 원본은 Git에서 제외됩니다. 복사본의 `alembic upgrade head`, `alembic check`, 무결성 검사 및 모든 기존 행 보존을 확인했습니다. 실제 개발 DB는 당시 Task·이벤트·회고·XP·태그 행이 0개였으며, 기록이 있는 구버전 DB 보존은 기존/신규 자동화 fixture로 별도 검증했습니다.

기존 README·패치노트·Compose 파일·실행 스크립트는 변경하지 않았습니다. 운영 DB는 개발/테스트에 사용하지 않습니다.

### 미루기 API

```text
POST /api/tasks/{id}/postpone
```

요청 본문을 생략하거나 `{}`를 보내면 기존과 같이 하루 미룹니다. 날짜를 지정하면 한 번에 이동합니다.

```json
{ "target_date": "2026-11-29" }
```

- 성공: 200, 기존 Task 응답 형식 유지
- 동일/이전 목표 날짜·완료 Task·기존 접근 제한·날짜 상한: 403 도메인 오류
- 잘못된 날짜·알 수 없는 필드·명시적인 `target_date: null`: 422
- 없는 Task: 404

Task 변경과 `UPDATED`/`POSTPONED` 이벤트 저장은 기존 직렬화 트랜잭션 하나로 처리합니다. 저장에 실패하면 변경 전체를 rollback합니다. 이벤트 전후 상태에서 Task ID·이전/이후 날짜·당시 태그를, `occurred_at`에서 발생 시각을 확인할 수 있습니다.

### 회고 API

기존 `GET /api/retrospectives`, `GET /api/retrospectives/{id}`만 확장하며 별도 분석 API는 없습니다. 신규 Snapshot의 `data.analysis` 구조는 다음과 같습니다.

```json
{
  "version": "v0.2.3",
  "coverage": {
    "status": "complete",
    "recording_started_at": "2026-11-01T00:00:00Z"
  },
  "tag_activity": [
    { "tag_id": 1, "name": "Python", "color": "#648ca6", "total": 5, "completed": 4, "incomplete": 1, "completion_rate": 80.0 }
  ],
  "postponements": {
    "postponed_tasks": 1,
    "total_postponements": 2,
    "postponed_days": 5,
    "by_tag": [
      { "tag_id": 1, "name": "Python", "color": "#648ca6", "postponed_tasks": 1, "total_postponements": 2, "postponed_days": 5 }
    ]
  }
}
```

`태그 없음`의 `tag_id`, `color`는 null입니다. `analysis`는 이전 Snapshot에서 생략될 수 있습니다. 기존 API 필드와 XP의 의미는 유지합니다.

## 개발 환경과 Git 상태

기준 커밋은 `main`/`origin/main`의 `5e8fcd9`입니다. README와 태그 배지 UI의 최신 변경까지 포함한 상태에서 `dev-v0.2.3`을 생성했습니다. 작업 시작 시 Working Tree는 깨끗했습니다.

## Known Limitations

- 분석 가능 시작 시각은 v0.2.2 이벤트 형식의 첫 증거로 보수적으로 판단합니다. 업데이트 시각이 별도 기록되지 않은 이전 기간의 0회 여부는 추정하지 않습니다.
- 기존 Snapshot은 Backfill하거나 재생성하지 않습니다. 분석이 빠진 예전 회고는 계속 해당 안내를 표시합니다.
- 모든 날짜의 이력을 복원하는 기존 집계 비용은 유지합니다. 새 분석에는 기간 종료 전 이벤트를 읽는 비용이 추가되며 대규모 이력의 증분 처리는 별도 과제입니다.
- 미루기 API는 멱등적이지 않습니다. UI의 요청 중 중복 클릭은 막지만 서로 다른 클라이언트의 성공 요청마다 날짜가 이동합니다.
- 태그 이름 변경·삭제·별도 관리, 완료 Task/여러 Task 일괄 미루기, AI 평가·소요 시간 분석, 태그별 XP·성장 공식 변경, Forest/Ocean 실제 성장 화면은 포함하지 않습니다.
