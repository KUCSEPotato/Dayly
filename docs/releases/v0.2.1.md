# v0.2.1 · 고정 회고와 성장 기록

이전 버전: [v0.2.0](v0.2.0.md). 서비스 기본 실행 방법: [README](../../README.md).

작업 브랜치는 `dev-v0.2.1`입니다. 이 브랜치가 v0.1 코드에서 분기되어 있어 로컬 `dev-v0.2.0`의 이력·개발 환경 소스를 먼저 작업 트리에 가져와 확장했습니다. Git 인덱스·커밋·브랜치 이력을 바꾸지 않았고 README의 기존 내용을 보존했습니다. GitHub 작업과 외부 배포는 수행하지 않았습니다.

## Added

- 일간·주간·월간 **고정 회고**와 영구 Snapshot. 원본 Task 수정·삭제 후에도 제목·설명·예정 날짜·완료 상태와 확정 통계가 유지됩니다.
- Snapshot이 없으면 종료된 기간을 조회할 때 자동 생성합니다. 서버가 자정에 꺼져 있어도 이벤트 이력으로 생성할 수 있습니다.
- 월요일~일요일 주간 회고, 실제 달력 월간 회고, 날짜별 그래프·완료/미완료 목록·가장 많이 완료한 날짜·월간 주차별 개수.
- 계획 달성률과 별도의 실제 최초 완료량, 해당 기간 획득 XP를 Snapshot에 함께 고정합니다.
- 워크스페이스의 **나만의 회고**, **나만의 세계** 메뉴와 달성률 카드의 일간/주간 회고 이동 버튼.
- Forest/Ocean 소개와 Coming Soon, 공통 누적 XP·레벨·다음 레벨 진행률·페이지를 나눈 지급 내역.

## Changed

- 기존 `TaskHistoryService.reconstruct(as_of) -> list[TaskRead]`, `events_between(start, end, task_id=None)`, `seoul_day_bounds()`를 재사용합니다. 현재 `tasks` 테이블로 과거 완료 상태를 추정하지 않습니다.
- 모든 Task/회고/XP 쓰기는 공통 `write_transaction()`을 사용합니다. SQLite는 읽기 전에 `BEGIN IMMEDIATE`, PostgreSQL은 공통 advisory transaction lock을 사용합니다.
- 신규 API는 Router에서 HTTP와 입력 검증, Schema에서 응답 계약, Model에서 영속성과 제약, Service에서 집계·트랜잭션을 담당합니다.
- 현재 성장 상태는 별도 합계 캐시 대신 변경 불가능한 지급 내역의 합으로 계산합니다. Forest와 Ocean이 동일한 값을 사용합니다.

## Fixed

- 지난 날짜를 나중에 완료해도 그 날짜의 확정 달성률에는 반영되지 않습니다.
- 종료 시각에 정확히 발생한 완료는 다음 날짜의 실제 수행량에 속합니다. 모든 기간은 서울 기준 날짜의 **[시작, 종료)**이며 이벤트 복원은 종료 시각 미만만 적용합니다.
- 주간·월간 비율은 날짜별 비율의 평균이 아닌 **완료 개수 합 / 전체 개수 합**입니다.
- 완료 체크 반복·API 재호출·동시 요청·서버 재시작으로 XP나 Snapshot이 중복 생성되지 않도록 고유 키와 트랜잭션을 적용했습니다.
- 이력 추적 이전의 기간을 `활동 기록 없음`으로 잘못 확정하지 않습니다.

## Database / Migration

신규 Alembic 리비전은 `0003_retrospectives_growth`입니다. `0002` 위에 다음 테이블만 추가하며 기존 Task·Task Events·ID를 변경하지 않습니다.

| 테이블 | 저장 내용 및 제약 |
|---|---|
| `history_coverage` | 추적 시작 UTC 시각을 저장하는 단일 행. 기존 최초 이벤트 시각, 이벤트가 없으면 마이그레이션 시각을 사용 |
| `retrospective_snapshots` | 종류·시작/종료 날짜·생성 시각·상태·개수·달성률·XP·전체 Task 사본·일별/주별 통계·실제 수행량 JSON. 종류+기간 고유 제약 |
| `experience_grants` | 지급 원인·Task/이벤트 ID·지급량·귀속 날짜·시각·정책 버전·중복 방지 키. 음수 금지 및 고유 키 |

Snapshot과 XP 지급 내역에는 ORM 보호와 DB UPDATE/DELETE 차단 트리거가 있습니다. 삭제 가능한 Task에 FK/Cascade Delete로 연결하지 않습니다. 일간 보너스는 `DAILY_BONUS`와 `earned_date`로 관련 일간 회고를 식별합니다.

기존 기간 Snapshot이 있으면 이력을 재생하거나 XP를 다시 계산하지 않고 저장된 결과를 반환합니다. 생성 중 오류가 나면 Snapshot과 그 요청에서 계산한 XP를 함께 rollback합니다.

기존 DB의 `alembic upgrade head` 재실행은 데이터나 시작 시각을 중복 생성하지 않습니다. 개발 Docker는 기존 시작 스크립트가 자동 적용합니다. v0.2.1 적용 전 개발 DB 백업을 `backend/data/backups/v0.2.1-before-20261106.db`에 보관했습니다. 백업은 Git과 Docker 빌드에서 제외됩니다. 운영 DB는 개발/테스트에 사용하지 않았습니다.

### 기간 및 복원 상태

- 일간: 선택 날짜 00:00~다음 날 00:00. 기본은 전날입니다.
- 주간: 월요일 00:00~다음 월요일 00:00. 기본은 직전 종료된 주이며 Dashboard의 Rolling 7 Days와 다릅니다.
- 월간: 1일 00:00~다음 달 1일 00:00. 기본은 직전 달이며 윤년을 포함합니다.
- 날짜 필드 `period_end`와 API `requested_period.end`는 **미포함 종료 날짜**입니다.
- 각 날짜의 Task 상태를 그 날짜 종료 시각 직전으로 복원한 뒤 예정 날짜로 필터링합니다. 한 Task가 여러 날짜의 종료 후 다음 날짜로 이동했다면, 서로 다른 날짜의 계획 기록에 각각 등장할 수 있습니다. 실제 수행량과 XP에서는 최초 추적 완료로 중복을 제거합니다.

| 상태 | 의미 |
|---|---|
| `ready` | 완전한 추적 기간에 계획이 있었음. 완료 0개는 정상 0% |
| `no_activity` | 완전한 추적 기간에 계획이 없었음. 비율은 null |
| `partial` | 추적 이전 날짜/시간이 포함됨. 확인 가능한 기록만 집계하며 전체 달성률로 간주하지 않음 |
| `unavailable` | 전체 기간이 추적 시작 이전. 개수와 비율은 null |
| `not_ended` | 아직 끝나지 않은 기간. Snapshot을 저장하지 않음 |

BASELINE 이전의 정확한 과거를 만들어 내지 않습니다. 기존 첫 이벤트가 하루 중간에 발생했다면 그 첫날도 보수적으로 `partial`로 표시합니다. 최초 이벤트 이전에 실제로 아무 일도 없었는지 확인할 수 없기 때문입니다.

### 임시 경험치 정책

정책 버전은 `v0.2.1-provisional`이며 수치는 확정되지 않았습니다.

| 설정 | 기본값 | 의미 |
|---|---|---|
| `XP_TASK_POINTS` | 10 | Task의 최초 추적 완료 XP |
| `XP_DAILY_CAP` | 100 | 완료 XP와 보너스를 합한 일일 상한 |
| `XP_BONUS_HALF` | 10 | 확정 계획 달성률 50% 이상 보너스 |
| `XP_BONUS_FULL` | 20 | 100% 달성 보너스. 50% 보너스와 중복하지 않음 |
| `XP_LEVEL_STEP` | 100 | 다음 레벨에 필요한 XP 증가 단위 |

- 완료를 처음 추적한 Task마다 `task:{id}:first`로 한 번만 지급합니다. 완료 해제·삭제 시 회수하지 않으며, 다음 날짜에 재완료해도 다시 지급하지 않습니다.
- `BASELINE`에서 이미 완료된 Task에는 과거 완료 XP를 추정해 지급하지 않습니다.
- 완료 XP는 **실제 이벤트 발생일**에 귀속합니다. 확정 보너스는 해당 예정 날짜의 회고에 귀속하며 날짜가 종료된 뒤 지급 가능합니다. 완전한 이력이 있는 날짜만 보너스 대상입니다.
- 하루에 작업을 많이 쪼개도 합계가 상한을 넘지 않습니다. 상한 때문에 지급량이 0이어도 키를 소비해 다음 날 같은 작업으로 보상을 우회하지 못합니다.
- 기존 지급량은 설정을 바꿔도 재계산하지 않습니다. 설정은 새 지급 건에 적용합니다. 레벨은 현재 레벨 설정과 누적 원장을 기준으로 계산합니다.
- 기본 레벨 시작 누적량은 Lv.1=0, Lv.2=100, Lv.3=300, Lv.4=600 XP입니다. 다음 레벨 필요량은 `XP_LEVEL_STEP × 현재 레벨`입니다.
- XP는 성장/회고 API를 조회할 때 누락된 이벤트와 종료된 날짜의 보너스를 동기화합니다. 지급 시각과 실제 귀속 날짜를 별도로 저장하므로 서버가 꺼져 있었어도 기간 집계가 유지됩니다.
- Snapshot을 만들기 전에 XP 동기화를 끝내고 그 기간의 지급 합계를 저장합니다. 이후 지급 내역이 늘어나도 기존 Snapshot의 XP는 고정입니다.

로컬 API는 `backend/.env`, 개발 Docker는 루트 `.env`의 `XP_*` 값을 읽습니다. `.env.example`의 설정 예시를 참고하세요.

## API

| Method / 경로 | 동작 |
|---|---|
| `GET /api/retrospectives` | 최근 종료된 세 종류의 누락 회고 생성 후 저장된 회고 목록 반환 |
| `GET /api/retrospectives?kind=daily` | 해당 종류의 최근 종료 기간 생성/조회 및 종류별 목록 |
| `GET /api/retrospectives?kind=weekly&date=2026-11-02` | 해당 날짜가 속한 주 조회. 미종료면 `not_ended` |
| `GET /api/retrospectives/{id}` | 저장된 Snapshot 상세. 재계산 없음 |
| `GET /api/growth/summary` | 누적 XP, 레벨, 다음 레벨 진행 상태, 현재 정책 |
| `GET /api/growth/history` | XP 지급 내역 |

회고 목록과 성장 내역은 `limit`(1~100), `offset`(0 이상)을 지원합니다. 회고 응답은 `items`, `total`, `requested_period`, `status`를 포함합니다. 날짜 조회에는 `kind`가 필요합니다. `date`를 생략하면 최근 종료 기간을 기본으로 삼습니다. 기간을 명시하면 해당 Snapshot 하나를 반환합니다. Task CRUD 응답과 기존 통계 API는 유지합니다.

## Known Limitations

- 추적 이전의 전체/일부 기간은 복원 불가/부분 기록으로 고정됩니다. 과거 이벤트를 임의로 만들거나 현재 Task로 빈칸을 채우지 않습니다.
- XP 수치와 레벨 정책은 임시입니다. 기존 지급액·Snapshot은 불변이며 변경된 정책으로 과거 보상을 다시 지급하지 않습니다.
- 과거 이벤트를 직접 관리 SQL로 삽입하는 작업은 지원하지 않습니다. 정상 앱 변경의 시간순 기록을 전제로 하며 수동 backfill 시 이미 확정된 Snapshot을 바꾸지 않습니다.
- 각 날짜에 대한 이벤트 재생과 원장 동기화를 수행하므로 대규모 장기 이력에 대한 증분 처리·쿼리 최적화는 후속 작업입니다. 현재는 로컬 단일 사용자 규모를 대상으로 합니다.
- SQLite에서 검증했습니다. PostgreSQL 실서버 검증은 수행하지 않았습니다.
- 실제 숲/나무·바다/고래 성장 이미지와 애니메이션, 테마별 환경 변화, 연간 초기화/보관함은 v1.0 범위입니다.

v1.0에서는 `RetrospectiveSnapshot`, `ExperienceGrant`, `RetrospectiveService`, `RetrospectiveAggregator`, `GrowthService`를 그대로 활용해 Forest/Ocean 연출을 추가할 수 있습니다. 테마별 경험치를 중복 저장하는 모델은 추가하지 않았습니다.
