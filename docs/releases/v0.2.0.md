# v0.2.0 · Task Events 기반 구축

이전 버전: [v0.1.0](v0.1.0.md) · 서비스 소개: [README](../../README.md).

개발 브랜치 `dev-v0.2.0`에서 구현했습니다. 기존 README의 사용자 변경은 유지하고 이 파일에 변경 내역과 개발 실행 방법을 기록합니다. main 병합 시 README에 추가할 상대 링크는 `docs/releases/v0.2.0.md`입니다.

## Added

- `task_events`: `CREATED`, `UPDATED`, `COMPLETED`, `UNCOMPLETED`, `DELETED`, `BASELINE` 이벤트.
- 각 이벤트에 Task ID, 전체 before/after 상태와 UTC 발생 시각 저장. 스냅샷은 `TaskRead`의 모든 필드를 포함하는 JSON이며, 삭제 후에도 이벤트가 유지됩니다.
- `TaskHistoryService.reconstruct(as_of)`: 이벤트만으로 기준 시각 직전의 Task 목록 복원.
- `TaskHistoryService.events_between(start, end, task_id=None)`: 향후 회고에서 재사용할 기간별 이벤트 조회.
- `seoul_day_bounds(day)`: 서울 기준 하루를 UTC 반열린 구간으로 변환.
- 상단 카드의 오늘/최근 7일 전환, 완료/전체 개수와 Progress Bar.

## Changed

- Task CRUD는 변경과 이벤트를 한 트랜잭션에서 commit합니다. 어느 쪽이든 실패하면 rollback합니다.
- 실제 필드 값이 같은 PATCH는 이벤트를 만들지 않으며 `updated_at`과 최초 `completed_at`도 바꾸지 않습니다.
- 제목·날짜·완료 여부를 한 번에 바꾸는 PATCH는 전체 변경을 담는 이벤트 **하나**로 기록합니다. 완료 여부가 바뀌면 `COMPLETED`/`UNCOMPLETED`를 우선하고, 그 외는 `UPDATED`입니다.
- 오늘 요약은 기존 주간 통계 응답의 오늘 행을 재사용합니다. 달력 선택과 독립적이며 기본 선택은 최근 7일입니다. 기존 CRUD와 공개 API 경로는 유지합니다.
- 패키지 및 OpenAPI 버전을 0.2.0으로 변경했습니다.

## Fixed

- 삭제한 가장 큰 Task ID를 SQLite가 다시 사용하는 경우 서로 다른 Task의 이력이 섞일 수 있어, ID 재사용을 막았습니다.
- SQLite 쓰기 트랜잭션을 `BEGIN IMMEDIATE`로 시작해 동시 수정 요청이 같은 과거 상태를 중복해서 before-state로 기록하지 않도록 했습니다. 다른 DB에서는 행 잠금을 사용합니다.
- 과거 상태는 `(occurred_at, id)` 순서로 복원하므로 타임스탬프가 같은 여러 이벤트도 순서가 결정됩니다.
- 상단 카드에서 이동 기능이 없는 화살표 장식을 제거했습니다. 회고 페이지로 연결하는 버튼은 추가하지 않았습니다.

## Development / Infrastructure

### 데이터베이스 마이그레이션

`backend/alembic/versions/0002_task_events.py`가 `0001` 위에 적용됩니다.

1. SQLite의 `tasks`를 Alembic batch copy로 옮기면서 `AUTOINCREMENT`를 적용합니다. 기존 ID·제목·설명·날짜·완료 상태·모든 타임스탬프와 제약·인덱스를 보존합니다.
2. `task_events`와 시간순/Task별 조회 인덱스, BASELINE 중복 방지 인덱스를 만듭니다.
3. 기존 Task마다 마이그레이션 시각의 `BASELINE` 하나를 저장합니다. before는 SQL NULL, after는 당시 전체 상태입니다. 기존 `created_at`을 이벤트 발생 시각으로 사용해 과거를 추정하지 않습니다.
4. SQLite/PostgreSQL의 UPDATE·DELETE 방지 트리거와 ORM 보호로 이벤트의 수정·삭제를 막습니다. 삭제 가능한 `tasks`에 대한 FK/Cascade Delete는 두지 않습니다.

`alembic upgrade head`를 다시 실행해도 리비전 확인으로 BASELINE이 중복 생성되지 않습니다. SQLite 작업은 데이터를 복사하는 스키마 변경이며 DB를 초기화하지 않습니다. Docker는 기존 시작 스크립트가 마이그레이션을 자동 적용합니다.

로컬 개발 DB를 직접 올리려면 다음을 실행합니다. 기본 DB와 Docker 개발 볼륨은 별개입니다.

```bash
cd backend
uv sync --locked
uv run alembic upgrade head
uv run alembic check
```

운영 DB에 적용하기 전에는 기존 README의 SQLite backup 방법으로 백업하세요. `alembic downgrade 0001`은 이벤트 테이블과 이력을 제거하므로 일상적인 롤백이나 개발 환경 종료에 사용하지 않습니다.

### 개발 서버: 8081

운영용 `compose.yaml`은 그대로 두고 **독립 파일** `compose.dev.yaml`을 사용합니다. 두 파일을 `-f compose.yaml -f compose.dev.yaml`로 병합하지 않습니다. Compose의 목록 병합으로 운영 포트/볼륨까지 연결되는 상황을 피하기 위한 선택입니다.

| 설정 | 기존 운영 | v0.2.0 개발 |
|---|---|---|
| Compose 파일 | `compose.yaml` | `compose.dev.yaml` |
| 프로젝트 | `dayly` | `dayly-dev` |
| 웹 외부 포트 | 기본 `127.0.0.1:8080` | `127.0.0.1:8081` |
| 컨테이너 | `dayly-…` | `dayly-dev-…` |
| 볼륨 | `dayly_data` | `dayly-dev_dev-data` |
| 컨테이너 내부 포트 | Nginx 80 / API 8000 | Nginx 80 / API 8000 |

Docker Desktop 실행 후 프로젝트 루트에서:

```bash
# 빌드 + 실행 + 준비 상태 대기
sh deploy/dev.sh

# 상태 / 로그 / 종료 (개발 DB 보존)
sh deploy/dev.sh ps
sh deploy/dev.sh logs
sh deploy/dev.sh down
```

접속: **http://localhost:8081**, API 문서: http://localhost:8081/docs.

Docker Compose만 직접 사용해도 같습니다.

```bash
docker compose -f compose.dev.yaml up -d --build --wait
docker compose -f compose.dev.yaml down
```

8081은 한 개발 환경이 사용합니다. 점유 중이면 Docker가 `port is already allocated` 또는 `address already in use`로 실패하며, 스크립트가 8081 충돌과 Docker 실행 상태를 확인하라는 안내를 출력합니다. 다른 개발 서버를 종료하고 다시 실행하세요. 스크립트는 운영 환경을 중지하거나 포트를 바꾸지 않습니다. 루트 `.env`의 운영용 `DAYLY_PORT`도 개발 포트에 영향을 주지 않습니다.

개발 환경은 운영 데이터와 개발 머신의 `backend/data/todo.db`를 자동으로 가져오지 않습니다. 이 브랜치에서는 운영용 Compose로 재빌드·기동하지 않아 기존 운영 볼륨을 마이그레이션하지 않습니다.

### 검증 명령

```bash
cd backend
uv run pytest -q
```

```bash
cd frontend
npm ci
npm run build
npx playwright install chromium
npm run test:e2e
```

pytest는 테스트마다 실제 마이그레이션을 적용한 임시 SQLite 파일을 사용합니다. Playwright 기본 설정은 별도 임시 DB와 8001/5174 포트에서 실행합니다. 운영 DB를 사용하지 않습니다.

`E2E_BASE_URL`을 지정하면 로컬 테스트 서버를 시작하지 않고 그 주소를 검증할 수 있습니다. 테스트는 Task를 생성·삭제하므로 **개인 기록이 없는 별도 검증 환경에만** 지정합니다.

검증 결과:

- pytest **56개 통과**: 기존 CRUD/통계 회귀와 이벤트 기록·양방향 rollback·append-only·동시 수정·과거 복원·시각 경계·기존 데이터 마이그레이션.
- Playwright **6개 통과**: 기존 사용자 흐름과 기간 전환·달력 선택 독립성·완료 후 요약 갱신·기록 없음·모바일 표시. 임시 로컬 서버와 별도 Docker 8081 환경에서 각각 실행했습니다.
- 엄격한 TypeScript/Vite 빌드와 Docker Backend/Frontend 빌드 성공, 컨테이너 `alembic check` 차이 없음.
- Docker에서 기존 v0.1.0 Task ID 42를 가진 검증 DB를 자동 마이그레이션해 데이터 보존과 BASELINE 복원을 확인했습니다. 검증 전용 컨테이너/볼륨은 정리했습니다.
- 운영 `dayly_data`의 DB를 읽기 전용으로 연결해 검증 전후 SHA-256이 같은 것을 확인했습니다. 기본 `dayly-dev`는 별도 빈 DB로 8081에서 실행했습니다.

## Known Limitations

- **BASELINE 도입 이전의 상태는 알 수 없습니다.** 해당 시점 이전을 복원하면 기존 Task도 결과에 없으며, 이후의 BASELINE부터 알려진 상태가 나타납니다.
- `reconstruct(as_of)`는 **`occurred_at < as_of`**인 이벤트를 적용합니다. 정확히 같은 시각의 이벤트는 모두 제외하며, 포함하려면 이후 시각을 사용합니다. 기간 조회는 **`start <= occurred_at < end`**입니다. 시간대 없는 naive datetime은 거절합니다.
- 복원은 전체 대상 이벤트를 순회합니다. 대규모 이력을 위한 Snapshot/증분 캐시는 이번 버전에 추가하지 않았습니다.
- 이력 기록 대상은 `TaskService`를 통한 정상 변경입니다. DB에 Task 행을 직접 수정하는 관리 작업은 자동으로 이벤트를 생성하지 않습니다.
- SQLite에서 자동 검증했습니다. PostgreSQL용 타입과 append-only 트리거는 포함하지만 PostgreSQL 실서버 검증은 수행하지 않았습니다.
- 이력 복원은 내부 Python Service입니다. 새 공개 이력 API, 회고 생성/화면/Snapshot, 경험치·레벨·성장 UI는 이번 버전에 포함하지 않습니다.
- 기존 최근 7일 상세 조회 제한과 로컬 단일 사용자 사용 범위는 유지합니다.

v0.2.1에서는 `TaskHistoryService.reconstruct()`, `events_between()`, `seoul_day_bounds()`와 기존 일일/주간 통계 API를 재사용할 수 있습니다. 새 테이블이나 공개 API를 미리 추가하지 않았습니다.
